定義一個模型：把積木疊起來

上一站學會了單一塊積木怎麼做，這站把好幾塊積木組裝成一個完整的模型——兩套框架在這裡的寫法差異是整個教學網站裡最明顯的一次。

兩套框架怎麼寫

PyTorch
import torch.nn as nn

class MyModel(nn.Module):
    def __init__(self):
        super().__init__()
        self.layer1 = nn.Linear(4, 8)
        self.relu = nn.ReLU()
        self.layer2 = nn.Linear(8, 1)

    def forward(self, x):
        x = self.layer1(x)
        x = self.relu(x)
        x = self.layer2(x)
        return x

model = MyModel()
TensorFlow
from tensorflow.keras import Sequential, layers

model = Sequential([
    layers.Dense(8, activation='relu', input_shape=(4,)),
    layers.Dense(1),
])

# 這就是完整的模型，不用再寫任何東西

為什麼 PyTorch 要寫一個 class，TensorFlow 不用

這組差異，直接呼應「自動微分」子地圖提過的「現學現做 vs 先寫劇本」哲學：

  • PyTorch 要你寫一個 class，裡面的 forward() 方法明確寫出「資料進來之後，要依序流過哪些層」——這給你完全的自由，forward() 裡面甚至可以寫 if 判斷式，讓資料根據情況走不同的路徑
  • TensorFlow 的 Sequential，顧名思義就是「依序排列」——你只要把每一層按順序放進一個清單，框架自動幫你把它們串起來，簡單到幾乎不用動腦，但代價是只能「依序往下流」，沒辦法在中間插入複雜的條件判斷

這不是誰比較好、誰比較差，是取捨：簡單直來直往的模型，Sequential 又快又好寫；結構複雜、需要分支或跳接的模型，PyTorch 的寫法（或 TensorFlow 自己也有的 Functional API，一種更有彈性但沒 Sequential 這麼直覺的寫法）會更合適。

一個小提醒：super().__init__() 不能漏

PyTorch 的 MyModel 裡第一行一定要寫 super().__init__()——這是在跟 Python 說「先讓我繼承來的父類別（nn.Module）把它自己份內該做的準備工作做完，我才能接著做我自己的設定」。忘記寫這行，程式通常會在你完全想不到的地方（例如呼叫 model.to(device) 時）噴出奇怪的錯誤，而不是在漏寫的那一行當場報錯。

工作中真的會踩到的坑

以為 Sequential 可以處理任何模型結構

新手很容易因為 Sequential 太好寫，想把所有模型都硬塞進這個格式——一旦你的模型需要「把兩條不同的資料路徑在中間合併」或「跳過幾層直接接到後面」（這類結構在稍微進階一點的模型裡很常見），Sequential 就做不到了，因為它的假設就是「資料只會乖乖依序往下流，一條路走到底」。遇到這種情況不用糾結，直接換用 TensorFlow 的 Functional API 或 PyTorch 的 class 寫法，不要硬凹 Sequential。

深入機制（進階，可選讀）

PyTorch 要求你寫一個繼承自 nn.Module 的 class，這背後其實是一個軟體工程裡常見的設計模式——理解這個模式，能幫你看懂為什麼框架要這樣設計。

1. 這是「模板方法模式」的應用

nn.Module 幫你把「怎麼管理模型的參數」「怎麼搬到 GPU」「怎麼存檔讀檔」這些共通的麻煩事都先寫好了，你只需要填兩個空格：__init__（宣告這個模型用到哪些層）跟 forward（資料怎麼流過這些層）。這種「父類別把通用流程都寫好，子類別只需要填寫特定細節」的設計方式，在軟體工程裡有個正式名稱叫 模板方法模式（Template Method Pattern）——框架控制整體流程，你只負責填入「這一題特有的部分」。

2. 為什麼 forward() 給你的自由，TensorFlow 的高階 API 給不了

因為 forward() 本質上就是一段普通的 Python 程式碼，你可以在裡面用任何 Python 語法——迴圈、條件判斷、甚至呼叫外部函式。這讓 PyTorch 很適合研究領域裡那些「結構會根據輸入動態改變」的模型。Sequential 這類高階 API 則是犧牲了這種彈性，換取「幾行就能定義完整模型」的速度——這正是「進階方向」子地圖裡要講到更複雜模型結構時，通常會改用更有彈性寫法的根本原因。
